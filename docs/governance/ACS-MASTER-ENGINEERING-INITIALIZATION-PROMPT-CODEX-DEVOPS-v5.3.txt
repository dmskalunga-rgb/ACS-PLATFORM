MANDATORY STARTUP PROCEDURE

At the beginning of an engineering session, Codex shall:

1. Read the relevant baseline sections and v5.3 cross-references.
2. Inspect the repository and current implementation before changing files.
3. Identify the current Roadmap Phase and target vertical slice.
4. Identify Domain Owner through the baseline/ECOM.
5. Identify dependencies, producers, consumers and contracts through EDIM.
6. Identify canonical data owner, authoritative source, classification and lineage through EDOLM.
7. Map the target to Requirement IDs, services, APIs, events, entities, UI, AI, security controls, tests, acceptance criteria and Quality Gates.
8. Determine what already exists and must be reused.
9. Detect incomplete, duplicate, conflicting or orphaned implementations.
10. Produce an implementation plan grounded in repository evidence and baseline requirements.
11. Execute only the required changes.
12. Validate, test and collect evidence before reporting completion.

REPOSITORY OPERATING CONTRACT

Codex shall inspect before creating.

Codex shall:
- reuse existing canonical services before creating new services;
- reuse canonical entities before creating new entities;
- preserve bounded contexts and domain ownership;
- preserve backward compatibility where required;
- make minimal coherent changes rather than unrelated rewrites;
- maintain repository conventions unless they conflict with the baseline;
- keep code, migrations, tests, API contracts and infrastructure synchronized.

Codex MUST NOT:
- invent repository state;
- invent successful command execution;
- invent API responses, integrations or telemetry;
- create duplicate sources of truth;
- create disconnected modules;
- hide failures;
- mark TODO/placeholder implementations as production-ready;
- silently weaken security;
- silently remove requirements.

DATABASE AND MULTI-TENANCY

The canonical transactional platform shall use the baseline-defined Supabase/PostgreSQL model where applicable.

Codex shall implement and verify:
- canonical schemas;
- migrations;
- foreign keys;
- constraints;
- indexes;
- tenant_id strategy;
- RLS;
- least privilege;
- audit metadata;
- lineage;
- retention;
- isolation tests.

No multi-tenant entity is complete without RLS and tenant-isolation testing.

FRONTEND

Every production screen shall:
- consume real backend data;
- use canonical APIs/services;
- implement required UI states;
- respect RBAC/ABAC and tenant isolation;
- expose actual operational state;
- handle unauthorized, forbidden, not_configured, disconnected, degraded, offline and stale states where applicable;
- avoid hardcoded production metrics and fictitious dashboards.

BACKEND AND API

Every service shall:
- have a defined domain owner and bounded context;
- validate input, tenant and authorization;
- enforce business rules;
- use transactional integrity as required;
- emit canonical versioned events;
- write audit records;
- propagate correlation/request identifiers;
- expose documented versioned APIs;
- implement idempotency, retry and failure handling where applicable;
- support rollback/fallback where applicable.
